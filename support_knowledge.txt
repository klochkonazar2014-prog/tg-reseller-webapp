## 📄 bot.py

### 🔍 Внутренняя логика и 'Секреты'
- Деньги/активы ходят через API запросы к `https://api.marketapp.ws/v1`, используя токен `MARKETAPP_TOKEN` для авторизации.
- Скрытые проверки:
  - Проверка наличия `user_id` в `OPERATOR_IDS` для получения юзернейма.
  - Проверка наличия кэша для юзернейма и обновление кэша каждые 3600 секунд (1 час).
  - Проверка статуса ответа от API (`200`, `429`, `503`) и повтор запроса при необходимости.
- 'Костыли' или особенности:
  - Использование глобальной сессии `_session` для ускорения запросов к API.
  - Повтор запроса до 3 раз при получении статуса `503` от API.
- Константы, лимиты или комиссии:
  - `MARKUP_PERCENT`: 20 (процентная наценка).
  - `ADMIN_ID`: 0 (по умолчанию, но может быть переопределен через переменную окружения).
  - `OWNER_WALLET`: не определена (переменная окружения).
  - `WEB_APP_URL` или `BACKEND_URL`: не определена (переменная окружения).

### ⚠️ Ловушки и Частые проблемы (Технический разбор)
- В строчке `async with session.get(f"https://api.marketapp.ws/v1{endpoint}", headers=headers, params=params, timeout=12) as response:` может произойти ошибка соединения с API.
- Если юзер жалуется на конкретный шаг, описанный в этом коде, можно ответить, что проблема может быть связана с ошибкой соединения с API или с неправильными данными, переданными в запрос.
- API может возвращать следующие неочевидные ошибки:
  - `403`: доступ запрещен (неправильный токен авторизации).
  - `400`: неправильный запрос (ошибка в параметрах запроса).
  - `500`: внутренняя ошибка сервера (ошибка на стороне API).

### 💡 Инсайды для ответов пользователю
- 'Внутренняя кухня': код использует глобальную сессию для ускорения запросов к API и повторяет запросы при получении статуса `503`.
- Инструкции для бота:
  - Если видишь в базе `username_{user_id}`, говори пользователю, что юзернейм уже кэширован.
  - Если видишь в базе `rate_limit`, говори пользователю, что необходимо подождать, так как достигнут лимит запросов к API.

### 📈 Флоу процесса (Подробно)
1. Пользователь совершает действие, которое требует запроса к API.
2. Код проверяет наличие кэша для юзернейма и обновляет кэш, если необходимо.
3. Код формирует запрос к API с необходимыми параметрами и авторизацией.
4. Код отправляет запрос к API и ожидает ответа.
5. Если ответ от API успешен (`200`), код обрабатывает данные и возвращает результат пользователю.
6. Если ответ от API не успешен (`429`, `503`), код повторяет запрос или возвращает ошибку пользователю.
7. Код записывает результат в базу данных, если необходимо.
8. Код возвращает результат пользователю.

## 📄 live_server.py

### 🔍 Внутренняя логика и 'Секреты'
- Деньги/активы ходят через взаимодействие с внешними API, такими как `toncenter.com` и `api.marketapp.ws`. 
- Скрытые проверки включают в себя проверку валидности `initData` с помощью HMAC-SHA256, а также проверку наличия и валидности токенов (`TOKENS`) и `BOT_TOKEN`.
- 'Костыли' или особенности, которые могут вызвать вопросы у юзера, включают в себя использование fallback-значений для токенов и `OWNER_WALLET`, если они не заданы в переменных окружения.
- Константы, лимиты или комиссии, зашитые в этом файле, включают в себя:
  - `USDT_JETTON_ADDRESS`: `"EQCxE6mUt_9S9clpu7R_6m09wYz3X0mR3GvK7N88m8_L3A1f"`
  - `MARKET_URL`: `"https://api.marketapp.ws/v1"`
  - `TOKENS`: список токенов, получаемый из переменных окружения или fallback-значений
  - `OWNER_WALLET`: кошелек владельца, получаемый из переменной окружения или fallback-значения
  - `PROXY_URL`: URL-прокси, получаемый из переменной окружения
  - `PORT`: порт, на котором работает сервер, равен `8001`
  - `BOT_TOKEN`: токен бота, получаемый из переменной окружения
  - Лимиты и комиссии, используемые в функции `calculate_markup`, включают в себя:
    - Для `p <= 0.01`: комиссия `0.05`
    - Для `0.01 < p <= 0.1`: комиссия `0.05`
    - Для `0.1 < p <= 0.25`: комиссия `0.1`
    - Для `0.25 < p <= 0.5`: комиссия `0.15`
    - Для `0.5 < p <= 1.0`: комиссия `0.25`
    - Для `1.0 < p <= 2.5`: комиссия `0.45`
    - Для `2.5 < p <= 5.0`: комиссия `0.75`
    - Для `p > 5.0`: комиссия `1.0`

### ⚠️ Ловушки и Частые проблемы (Технический разбор)
- В строчке `h = hmac.new(secret_key, data_check_string.encode(), hashlib.sha256).hexdigest()`, если `initData` невалидно или не содержит необходимых полей, функция `validate_init_data` вернет `None`.
- Если юзер жалуется на конкретный шаг, описанный в этом коде, необходимо проверить логи и переменные окружения, чтобы определить причину проблемы.
- API может возвращать следующие неочевидные ошибки:
  - `403`: доступ запрещен, возможно из-за невалидного токена или отсутствия необходимых полей в запросе
  - `400`: невалидный запрос, возможно из-за неверного формата данных или отсутствия необходимых полей
  - `500`: внутренняя ошибка сервера, возможно из-за проблем с подключением к внешним API или базе данных

### 💡 Инсайды для ответов пользователю
- 'Внутренняя кухня': код написан на Python, использует фреймворк `aiohttp` для создания веб-сервера и взаимодействия с внешними API. 
- Конкретные инструкции для бота: если в базе данных есть запись с `user_id`, соответствующим `id` пользователя, бот должен вернуть информацию о балансе пользователя.

### 📈 Флоу процесса (Подробно)
1. Пользователь совершает действие, отправляя запрос на сервер.
2. Сервер получает запрос и проверяет валидность `initData` с помощью функции `validate_init_data`.
3. Если `initData` валидно, сервер извлекает `user_id` из `initData` и проверяет наличие необходимых полей в запросе.
4. Если все поля присутствуют, сервер отправляет запрос на внешнее API, чтобы получить необходимую информацию (например, баланс пользователя).
5. Сервер получает ответ от внешнего API и обрабатывает его, возможно изменяя баланс пользователя или создавая новую запись в базе данных.
6. Сервер возвращает ответ пользователю, содержащий необходимую информацию (например, баланс пользователя).

## 📄 database.py

### 🔍 Внутренняя логика и 'Секреты'
– Как именно здесь ходят деньги/активы? Какие скрытые проверки есть?
  * Деньги и активы хранятся в таблицах `users` и `items`. В таблице `users` есть столбец `balance`, который хранит текущий баланс пользователя. В таблице `items` есть столбцы `original_price` и `price_per_day`, которые хранят первоначальную цену и цену за день аренды соответственно.
  * Скрытые проверки включают проверку наличия столбцов в таблицах и добавление их, если они отсутствуют. Это делается для поддержки миграции базы данных.

– Есть ли 'костыли' или особенности, которые могут вызвать вопросы у юзера?
  * Да, есть особенности, которые могут вызвать вопросы у юзера. Например, столбец `auto_relist` в таблице `items` по умолчанию равен 1, что означает, что продавец включил автоматическое повторное выставление товара на продажу. Это может вызвать вопросы у юзера, если он не понимает, почему его товар повторно выставляется на продажу.

– Какие константы, лимиты или комиссии зашиты в этом файле? (выпиши цифры)
  * Константы и лимиты:
    + `min_duration`: 86400 (1 день)
    + `max_duration`: 2592000 (30 дней)
    + `refund_amount`: 0.14 (комиссия за возврат средств)
  * Комиссии:
    + `referral_commission`: 0 (комиссия за рекомендацию, по умолчанию равна 0)

– Что отвечать, если юзер жалуется на конкретный шаг, описанный в этом коде?
  * Если юзер жалуется на конкретный шаг, необходимо проанализировать код и понять, какой именно шаг вызывает проблему. Например, если юзер жалуется на автоматическое повторное выставление товара на продажу, необходимо объяснить ему, что это происходит из-за значения столбца `auto_relist` в таблице `items`.

– Если это API — какие неочевидные ошибки оно возвращает (403, 400, 500) и что они ЗНАЧАТ на самом деле?
  * Ошибки:
    + 403: Forbidden (доступ запрещен)

  * Эти ошибки могут возникать из-за различных причин, таких как отсутствие доступа к таблицам или столбцам, неправильные запросы или внутренние ошибки сервера.

### 💡 Инсайды для ответов пользователю
– Расскажи 'внутреннюю кухню': почему сделано именно так?
  * Код написан на языке Python и использует библиотеку `aiosqlite` для взаимодействия с базой данных SQLite. Это позволяет создавать асинхронные запросы к базе данных, что улучшает производительность приложения.
  * Таблицы `users`, `items` и `orders` используются для хранения информации о пользователях, товарах и заказах соответственно. Это позволяет эффективно управлять данными и выполнять запросы.

  * Если видишь в базе `auto_relist` = 1, говори пользователю: "Ваш товар будет автоматически повторно выставлен на продажу после окончания аренды."

### 📈 Флоу процесса (Подробно)
– Опиши пошагово, что происходит в коде, когда пользователь совершает действие. Где создается запись, куда летит запрос, какой статус меняется.

    2. Выполняется запрос к таблице `users` для получения информации о пользователе.

    6. Выполняется запрос к таблице `orders` для создания новой записи о заказе.
    7. Записи в таблицах `users`, `items` и `orders` обновляются в соответствии с действиями пользователя.
    8. Статус заказа меняется на "pending_payment" или "paid" в зависимости от результата оплаты.
